# 8-优化PAML大于ML进行校正方案：总设计与长期记忆

## 1. 项目背景

这个项目的根本动机很明确：PAML 在超大树上一次性直接运行时，速度慢、内存压力大，或者根本跑不出来。因此当前工程采取的是“先拆树、再分别跑 PAML、最后合并”的分治思路。

当前 `7-PAML对ML进行校正` 版本的主流程是：

1. split
2. run PAML
3. merge
4. ultrastandard

当前版本已经能够生成一棵超度量树，并且 `4-run_ultrastandard_pipeline.sh` 已经在 `7` 目录内验证跑通。但是，这一结果只说明工程上“能产出一棵超度量树”，并不自动意味着方法学上已经逼近“如果整棵大树能直接 full-tree PAML 运行时”的结果。

这个目录 `8-优化PAML大于ML进行校正方案` 的使命，是在保留现有工程可运行基础的前提下，逐步把方法学改得更合理、更接近 full-tree PAML 的全局枝长结果。

## 2. 当前版本的数据流

当前版本可以用最通俗的话概括为：

1. 先把一棵大树切成很多小块
2. 每个小块单独跑 PAML
3. 跑完以后把这些小块直接拼回去
4. 拼回去后发现整棵树往往不是超度量树
5. 最后再通过 ultrastandard 把它压成一棵超度量树

也就是：

```text
大树
-> split
-> 多个小树独立跑 PAML
-> 直接 merge
-> 得到 merged_tree
-> 发现不是 ultrametric
-> 再做 ultrastandard
-> 得到 ultrametric tree
```

当前版本最核心的问题不在于“最后不是超度量”，而在于：

- 各个子树虽然都跑了 PAML，但它们得到的枝长不一定处在同一个全局尺度上
- 这些枝长被直接拼回去之后，出现“局部尺度不一致”
- 最后的超度量化，本质上是一种后修补，只是在最后一步把树压平，而不是从一开始就保证全局尺度统一

换句话说，当前版本更像是：

- 先拼树
- 再矫正

而不是：

- 先统一标准
- 再拼树

## 3. 新版本的目标数据流

新的目标数据流必须明确区分两类产物：

1. **主产物**：近似 full-tree PAML 的全局非超度量 ML 树
2. **派生产物**：从主产物投影得到的超度量树

新数据流应当是：

```text
大树
-> split（每个子树保留 overlap anchors）
-> 每个子树独立跑 PAML
-> 先做全局尺度统一
-> merge 成 merged_ml_tree
-> 再从 merged_ml_tree 投影出 merged_ultrametric_tree
```

也就是说：

1. 大树切块
2. 每个子树不再是完全独立的，会故意保留一些 overlap anchors
3. 每个子树独立跑 PAML
4. 跑完以后不立刻合并，而是先用这些共享参照点做全局尺度统一
5. 先得到一棵尽量接近 full-tree PAML 的 `merged_ml_tree`
6. 如果后续分析需要超度量树，再单独做一次超度量投影

这里必须强调：

- **主产物不是超度量树**
- **超度量树是派生产物**
- 超度量化不再是主问题，而是最后一步

## 4. 旧版本 vs 新版本的差别

最通俗的说法如下。

### 旧版本

旧版本做的事情像这样：

- 把大地图切成很多小图
- 每张小图各自量尺寸
- 最后直接拼起来
- 拼完发现比例不统一，再整体拉伸压缩

一句话：

**先拼树，再矫正。**

### 新版本

新版本想做的事情像这样：

- 把大地图切成很多小图
- 每张小图里都保留一些共同地标
- 先用这些共同地标把比例尺对齐
- 再把小图拼起来

一句话：

**先统一尺子，再拼树。**

### overlap anchors 的通俗作用

overlap anchors 的作用就是：给每个子树保留一些“共同地标”。

这样在不同子树跑完 PAML 后，就可以比较：

- 这个子树整体是不是偏长
- 这个子树整体是不是偏短
- 它应该缩放到什么程度，才能和别的子树处在同一个全局尺度上

如果没有 overlap anchors，那么很多子树在合并前就像是：

- 各自拿不同尺子量出来的结果

这正是当前版本后期会出现非超度量、局部过深、局部过浅等问题的根源之一。

## 5. 方法学上的核心判断

当前方法学上的核心判断，必须明确记录如下：

1. 当前流程最值得改进的，不是“怎么强行把最后结果变成超度量树”
2. 真正值得改进的是“不同子树独立跑 PAML 后，如何把它们的枝长拉回同一个全局坐标系”
3. target-only scaffold 深链不应继续被视为可靠的时间或长度依据
4. 主树与超度量树必须拆成两个产物：
   - `merged_ml_tree`
   - `merged_ultrametric_tree`

更具体地说：

- `merged_ml_tree` 应该承担“尽量接近 full-tree PAML”这个目标
- `merged_ultrametric_tree` 应该承担“满足 ultrametric、方便后续分子钟或外部时间校准”这个目标

不能再把这两个目标混在一棵树里同时解决。

## 6. 后续计划的优先顺序

后续默认按以下顺序推进：

1. 改 split，引入 overlap anchors
2. 改 merge，先统一尺度得到 `merged_ml_tree`
3. 改 ultrastandard，把它改造成“超度量投影层”


- split 是数据设计层
- merge 是全局尺度统一层
- ultrastandard 是投影层

不能把这些层混在一起修改，否则很难知道误差是从哪一层引入的。

## 7. 当前已经验证过的事实

以下事实已经确认，应当长期保留在文档中：

1. 当前 `7-PAML对ML进行校正` 已经能跑通 `4-run_ultrastandard_pipeline.sh`
2. 当前 ultrastandard 的确可以输出一棵超度量树
3. 当前 ultrastandard 输出的超度量树通过了拓扑校验与 ultrametric 校验
4. 但这并不代表当前结果已经逼近 full-tree PAML


## 8. 明确约束

后续所有设计都必须遵守以下约束：

1. 拓扑必须始终严格继承原始大树
2. 当前不追求绝对时间
3. 当前追求的是“尽量接近整树 PAML 的全局一致枝长”
4. 允许 overlap anchors
5. benchmark 树规模默认考虑：
   - 300 tips
   - 500 tips
   - 800 tips
   - 1000 tips

其中第 2 条尤其重要：

- 当前阶段不追求绝对时间尺度
- 因为哪怕 full-tree PAML 跑通，后续通常也还要结合外部校准或分子钟模型来得到绝对时间
- 当前阶段更重要的是让枝长在全局上尽可能一致、可比较

另外，split 层已经完成了第一轮**不改变预期结果**的性能优化，重点是两件事。

第一，`1-run_split_pipeline.sh` 现在新增了 `Stage 0/2: precompute_split_context`。

这个阶段会先对输入大树做一次统一预处理，并把后续 split 反复需要的信息写入：

- `output/split/intermediate/rooted.tree`
- `output/split/intermediate/split_context.json`
- `output/split/split_precompute.log`

当前 `split_context.json` 至少承担以下作用：

- 绑定当前输入树的哈希与预处理结果
- 记录已经规范化后的 rooted binary tree 上下文
- 为后续 target partition 和 local anchor 选择提供可复用的距离相关缓存

第二，local anchor 选择已经不再像旧版那样在每个 target subtree 上大量重复调用 `tree.distance()`。

当前实现已经改成：

- 先计算并缓存节点到 root 的距离
- 先缓存 tip 顺序与 clade 对应的 root distance
- 后续 anchor 选择直接读取这些上下文

这意味着：

- local anchor 的**选择规则没有变**
- 预期输出结果没有变
- 但最贵的 patristic distance 重复计算被明显减少

第三，`validate_phylo_split.py` 已经从“默认全量重算”改成“双模式”。

当前支持：

- `validation_mode = fast`：默认
- `validation_mode = strict`：保留

其中：

- `fast` 模式只做结构校验、关键字段复核、tip set/hash/manifest 一致性检查
- `strict` 模式才重新从原始树出发重算 target partition 与 paml subtree 设计并逐项比对

这样做的目的很明确：

- 平时开发与重跑时，避免 validation 又把最贵的 split 设计过程完整重做一遍
- 需要审计算法正确性时，仍然可以切回 `strict`

### 10.2 PAML 层已经落地的更新

当前 `2-run_paml_pipeline.sh` 已支持双模式：

1. `real`
2. `fake`

当前默认走的是 `fake` 模式，配置项在：

- `conf/2-paml.yaml`
- `paml.execution_mode: "fake"`

当前 fake 模式不是随便乱造树，而是遵守以下规则：

1. fake 输出树的拓扑必须与 split 产生的原始诱导子树拓扑一致
2. fake 输出树的枝长允许变化
3. fake 输出树会被处理成超度量树
4. fake 输出结果直接写入 `output/paml/analysis_trees/`
5. backbone-only 的 fake 超度量树也会同步生成

当前 fake 模式已经能正式产出：

- `output/paml/analysis_trees/*.nwk`

这意味着当前开发已经不再依赖真实 baseml 才能推进 merge 和 ultrastandard 的代码重构。

### 10.3 merge 层已经落地的更新

- `merged_ml_tree` 是 merge 的主产物
- `merged_ultrametric_tree` 是 ultrastandard 的派生产物
- ultrastandard 当前读取的是 `merged_ml_tree.nwk`
- ultrastandard 当前做的是“固定拓扑下的超度量投影”

当前第一版投影层的实现方式是：

1. 读取 `output/merge/merged_ml_tree.nwk`
2. 保持拓扑不变
3. 当前默认通过 `constrained_height_fit` 方式，把内部节点高度和终端高度一起拟合到超度量空间

这说明 ultrastandard 已经从旧的“补救式重新 graft”正式转向“从主产物做超度量投影”。
同时也说明当前投影算法已经不再只是“只延长 terminal branch”的最初版本。

## 11. 当前正在推进的下一步

当前**暂时不做 benchmark**。

当前下一步的核心任务已经明确，不要跑偏：

### 11.1 当前正在做的事情

当前已经完成了 merge 第一版尺度统一：

- 已从旧的 `identity_graft`
- 进入到第一版 `median_log_path_ratio`

也就是：

- 不再默认把每个子树直接按原尺度 graft 回去
- 而是先利用 overlap anchors 和 backbone 参考 tip
- 估计每个子树自己的 scale factor
- 先把整个 analysis tree 拉回统一尺度
- 然后再用于 backbone 聚合和 target graft

### 11.2 当前这一步的意义

这一改动已经成为“先统一尺子，再拼树”的第一版真正落地。

它的意义在于：

1. merge 不再只是机械拼接
2. overlap anchors 开始真正参与尺度统一
3. `subtree_scale_report.tsv` 不再只是形式接口
4. 后面即使不做 benchmark，也能先在代码结构上把新方法走通

### 11.3 当前还没有做的事情

当前下一步更靠前的任务变成：

- 继续加强 `constrained_height_fit` 的稳定性与拟合质量
- 细化 `ultrametric_projection_report.tsv`，让边级扭曲报告更完整

当前仍然没有做：

- benchmark
- benchmark 误差评估
- full-tree PAML 对照
- 更高级的 backbone-plus-overlap 联合回归
- 更成熟的 ultrametric projection 优化与误差评价

所以必须明确：

- 当前代码已经进入“新方案实现阶段”
- 但仍然处于“第一版尺度统一落地中”
- 还不能宣称方法学已经最终完成

另外，split 阶段当前的主要剩余耗时已经发生变化。

在完成这轮优化之后，split 现在已经不再主要耗在 local anchor 选择，而更多耗在：

- `gotree prune`
- `gotree reroot outgroup`
- 大量子树文件的实际写出

也就是说，split 最明显的 Python 侧热点已经先被处理掉了；如果后面还要继续提速，重点更可能落在子树构建 I/O 和外部 `gotree` 调用层面，而不再是 anchor 选择本身。
